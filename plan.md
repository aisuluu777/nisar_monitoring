ТЗ: платформа мониторинга склонов на открытых данных NASA
Nov 14, 2026 · @Alatoo
1. Цель, охват и принципы
Платформа раз в цикл съёмки получает открытые данные NASA, сравнивает состояние участков земной поверхности с их собственной историей и показывает, где поведение отличается от нормы. Результат нужен местной администрации, МЧС и государственным органам, а также исследователям и статистикам. Это система раннего внимания к склонам, а не прогноз оползней.
В MVP входит
• Пилот на крупных районах всех областей Кыргызстана; сетка ячеек накрывает всю территорию каждого района.
• Автоматический сбор данных NASA (радарное смещение, влажность почвы, нарушение растительности, осадки, известные оползни).
• Отслеживание ледников района: скорость движения льда, снежный покров, изменение высоты поверхности; те же четыре статуса, что у ячеек (раздел 4.1).
• Расчёт «нормы» для каждой ячейки и отклонений от неё; четыре статуса: зелёный, жёлтый, красный, серый («недостаточно данных»).
• Три интерфейса: дашборд администрации, панель МЧС и государственных органов, открытый API с выгрузками для исследователей.
• ИИ-объяснитель: простые тексты о том, что изменилось и почему участок получил такой статус (раздел 7).
• Журнал решений специалистов: «подтверждено» или «ложная тревога».
• Проверка на прошлых событиях района (ретроспектива) до публикации любых уровней.
Вне MVP
• Прогноз оползней и расчёт вероятности.
• Режим «любая точка мира» и охват нескольких районов.
• Личные кабинеты жителей и мобильное приложение.
• Автоматическая рассылка тревог населению.
Принципы честности данных
1.  Каждый показатель на экране сопровождается паспортом: источник, дата, версия продукта, качество.
2.  Система показывает отклонение от нормы и не утверждает, что участок опасен или безопасен.
3.  Данные NISAR пока имеют статус Provisional; сравнение с прошлым не смешивает продукты разной зрелости.
4.  Участок без достаточных данных получает серый статус, а не зелёный.
5.  Решение о реальных действиях всегда принимает человек; система помогает ему найти участки.
6.  Нет персональных данных жителей; все данные относятся к местности, а не к людям.

Ключевые сценарии
1.  Сотрудник администрации открывает дашборд, видит жёлтые и красные ячейки, читает объяснение и передаёт участок специалисту.
2.  Специалист МЧС открывает участок, смотрит ряд смещения и осадков, помечает «подтверждено» или «ложная тревога» и добавляет комментарий.
3.  Исследователь получает через API ряд смещения по ячейкам за период вместе с версией обработки и паспортом.
4.  Любой авторизованный пользователь задаёт вопрос по данным («что изменилось в этом районе за месяц») и получает ответ ИИ с указанием использованных данных.
3. Архитектура
Система собирается из слоёв, каждый из которых можно менять отдельно. Внешние API опрашивает только конвейер; аналитика, ИИ и интерфейсы работают с уже сохранёнными данными, поэтому сбой NASA не останавливает платформу.
1.  Источники — NASA и открытые данные (раздел 4).
2.  Конвейер — по расписанию находит новые снимки, режет данные по ячейкам сетки района и пишет результат с паспортом (раздел 5).
3.  Хранилище — растровые файлы и база PostgreSQL с PostGIS: ячейки, ряды показателей, статусы, журнал решений, версии.
4.  Аналитика — считает «норму» и отклонения, присваивает статусы (раздел 6).
5.  ИИ-объяснитель — превращает уже посчитанные факты в понятный текст и отвечает на вопросы по данным (раздел 7).
6.  API (FastAPI) — единая точка доступа с ролями (раздел 8).
7.  Интерфейсы — дашборд администрации, панель МЧС и государства, открытый API для исследователей (раздел 9).
Правило, которое держит всё вместе: решение об аномалии принимает аналитика на проверяемых числах, ИИ только объясняет их. Токены Earthdata и ключ LLM-провайдера хранятся только на сервере, в .env.
Схема читается сверху вниз: ИИ стоит после аналитики и видит только уже посчитанные факты, а все интерфейсы получают данные через API с ролями.

4.1. Ледники
Ледники отслеживаются как отдельные объекты (полигоны), а не как ячейки сетки: контуры берутся из каталога, затем для каждого ледника считаются сигналы и статус по тем же правилам, что у ячеек (норма, отклонение, серый статус при нехватке данных). Статус означает «нужна проверка специалиста» и не является прогнозом.
Данные (всё, что помечено «проверить», сверяется на этапе 0):
• Контуры ледников: Randolph Glacier Inventory (RGI 7, NSIDC) и/или GLIMS; проверить версию и покрытие Кыргызстана (проверить).
• Скорость движения ледника: ITS_LIVE (NASA, по оптическим и радарным парам); резкое ускорение относительно собственной нормы — сигнал подвижки (проверить доступ и покрытие).
• Снежный покров: MODIS/VIIRS (NSIDC), для сезонной нормы и отличия снега от льда (проверить продукт).
• Изменение высоты поверхности: ICESat-2 (ATL06/ATL15), медленный сигнал, раз в сезон (проверить).
• Ледниковые озёра и риск прорыва озёр (GLOF): вне MVP, нужны отдельные данные и эксперт.
Для каждого ледника хранятся статичные признаки (площадь, высотный диапазон, экспозиция, привязка к району и области) и ряды сигналов с паспортом продукта. Ограничение: скорость ледника считается только там и тогда, где есть пары снимков без облаков; иначе серый статус.

Доступ к данным NISAR без скачивания целых файлов
Документация ASF показывает потоковое чтение: asf_search находит гранулу, fsspec и xarray (движок h5netcdf) читают только нужные диапазоны байт. Внутренние пути HDF5 в ТЗ намеренно не указаны: на этапе 0 разработчик открывает один настоящий файл и фиксирует их.
5. Конвейер и хранилище
Конвейер — отдельное Python-приложение (pipeline/). Запускается по расписанию и вручную: python -m pipeline run --district <id>. Все шаги идемпотентны: повторный запуск на тех же данных даёт тот же результат. Планировщик (cron, Prefect или Airflow) выбирает команда.
Сетка ячеек
Территория района делится на ячейки одинакового размера (размер — параметр, начальное значение подбирается на этапе 0 с учётом разрешения 80 м у GUNW). У каждой ячейки есть статичные признаки: средний и максимальный уклон, доля леса, воды и застройки, привязка к селу и району.
Шаги конвейера на каждый цикл
1.  Поиск. asf_search находит новые GUNW по полигону района. Если новых нет, цикл пропускается без ошибки.
2.  Чтение окна. Потоково читаем только район: развёрнутую фазу, когерентность, маску связных компонент, ионосферную фазу.
3.  Контроль качества. Маска по когерентности и связным компонентам; плоская «рампа» (дрейф от атмосферы и орбиты) вычитается по устойчивой зоне; продукты с слишком сильной рампой отмечаются «низкое качество».
4.  Перевод в смещение. d = −λ·φ / (4π), где λ — длина волны L-диапазона (около 24 см). Знак проверяется на этапе 0 на известном событии.
5.  Агрегация по ячейкам. Для каждой ячейки: медианное и верхний квантиль смещения, доля надёжных пикселей, флаги качества.
6.  Дополнительные сигналы. Влажность почвы (SME2), нарушение растительности (DIST-S1), суммы осадков за 7 и 30 дней перед каждой датой съёмки — тоже по ячейкам.
7.  Запись. Результаты и паспорт продукта пишутся в хранилище; запускается аналитика (раздел 6) и генерация текстов (раздел 7).
История для «нормы»
У NISAR история пока короткая, поэтому «норму» по сезонам строим по Sentinel-1 (HyP3, временной ряд в MintPy) и храним как отдельную линию данных. Ряды разных спутников и разных версий продукта не объединяются в один: каждый хранится отдельно, сравнение делается внутри своего семейства. Какие пары продуктов можно сравнивать, решается на этапе 0.

6. Аналитика: как мы сравниваем с прошлым
Ядро анализа — объяснимая статистика на библиотеках. Каждый статус ячейки сопровождается списком причин с числами, которые можно проверить вручную. Машинное обучение в MVP не принимает решения, так как нет размеченных событий для обучения и для проверки.
Как считается «норма» и отклонение
1.  Норма ячейки. Для каждого сигнала строится сезонная норма: медиана и устойчивый разброс (MAD) для похожего периода года; при длинной истории — разложение ряда на тренд, сезон и остаток (STL).
2.  Отклонение. Новое значение сравнивается с нормой: устойчивый z-балл и перцентиль. Важно и отклонение от «соседей»: если движется вся сцена сразу, это похоже на атмосферу, а не на склон.
3.  Смещение. Считаются кумулятивное смещение и скорость; смена режима ищется алгоритмом точек изменения (ruptures).
4.  Пространственный фильтр. Соседние ячейки с отклонением объединяются в кластер; одиночные выбросы помечаются как слабые сигналы.
5.  Осадки, влажность почвы, растительность. Сравниваются с климатической нормой того же сезона; ячейки, где SME2 не даёт оценки (снег, мёрзлый грунт), не участвуют в этом сигнале.
6.  Рельеф — контекст, не сигнал. Крутизна и покрытие помогают объяснить ситуацию, но не меняют статус сами по себе.
Уровни внимания (предварительные правила)
Пороги — параметры; числа подбираются на ретроспективе и утверждаются вместе с контактом из администрации или МЧС.

Когда появится ML
Когда в журнале решений накопятся подтверждённые случаи и ложные тревоги, можно запустить модель в «теневом» режиме: она считает, но не влияет на статусы, и включается только если лучше правил на ретроспективе.
Проверка на прошлых событиях (ретроспектива)
1.  Собираем известные события района из NASA COOLR и от контакта из администрации или МЧС.
2.  Разделяем историю на два периода: на первом подбираем пороги, на втором честно проверяем, не меняя пороги.
3.  Считаем, сколько событий были предварены жёлтым или красным статусом, за какое время до события, и сколько было ложных тревог.
4.  Пропущенные события и неудачи показываются в отчёте наравне с удачами.
5.  Без такого отчёта уровни внимания наружу не публикуются.
7. ИИ-объяснитель
ИИ (языковая модель) нужен, чтобы человек без подготовки понял, что изменилось и почему участок получил статус. Он не принимает решений, не меняет статусы и не делает прогнозов: статус присваивает аналитика (раздел 6), а ИИ лишь пересказывает уже посчитанные факты.
Три задачи
1.  Бюллетень участка. Короткий текст про ячейку или группу ячеек после каждого цикла: что изменилось по сравнению с нормой и прошлым циклом, почему этот статус, что известно, что неизвестно.
2.  Сводка по району. Один текст на цикл: сколько ячеек в каждом статусе, что изменилось, на что обратить внимание в первую очередь.
3.  Вопросы по данным. Чат: «что изменилось за месяц в этом районе», «почему эта ячейка жёлтая», «покажи самые быстро движущиеся участки».

Что подаётся на вход
Только структурированный «пакет фактов» (JSON): идентификатор ячейки, период, статус и причины с числами и единицами, норма и прошлый цикл, флаги качества, источники с датами и версиями. Никаких персональных данных и сырых снимков в запрос к провайдеру не уходит.
Формат бюллетеня
В каждом тексте три обязательных блока: «Что мы видим», «Чего мы не знаем», «На чём основано» (источники и даты). Пример формы с подстановками (числа берутся из пакета фактов, не из шаблона): «За последние 12 дней поверхность в этой ячейке сместилась на {N} см вдоль луча спутника. Обычно в это время года бывает около {M} см. Дождей было больше обычного. Это не прогноз — участок стоит передать специалисту для проверки».
Защита от ошибок
1.  Проверка чисел. Код извлекает все числа из текста и сверяет с пакетом фактов (с допустимым округлением). При несовпадении — одна попытка перегенерации, потом шаблонный текст.
2.  Запретные утверждения. Текст не должен содержать прогнозов «оползень будет», утверждений «безопасно» и рекомендаций об эвакуации; список слов и оборотов проверяется кодом и дополняется вместе с МЧС.
3.  Ограничения данных. Если есть флаги качества или статус Provisional, в тексте обязательна фраза об этом. Для серого статуса текст говорит «данных недостаточно», а не «всё в порядке».
4.  Резерв без ИИ. Если провайдер недоступен или проверка не пройдена, платформа показывает шаблонный текст из тех же фактов. Система полностью работоспособна без ИИ.
5.  Утверждение человеком. Тексты, которые уходят за пределы платформы (отчёты, рассылки, публичный уровень), сначала получают статус «черновик» и публикуются после одобрения сотрудником. Внутри дашбордов текст помечается «сгенерировано ИИ».
Чат по данным
• Модель вызывает только функции «только чтение» нашего API (статус ячейки, ряд значений, сравнение периодов, список ячеек по статусу); записывать, менять статусы или ходить по ссылкам она не может.
• Модель получает только то, что может видеть текущая роль пользователя.
• Вопрос пользователя считается недоверенным текстом: инструкции в нём не меняют правила.
• На просьбы прогноза или совета об эвакуации ответ: «этого система не делает, обратитесь к специалистам», и показывает данные по этому участку.
Эксплуатация
• Провайдер языковой модели подключается через один абстрактный модуль; ключ в .env; выбор модели и провайдера — решение команды.
• Бюллетени генерируются один раз на ячейку и цикл и кэшируются, только для ячеек со сменой статуса или в жёлтом и красном статусе; чат ограничен по частоте запросов.
• Все запросы, ответы и результаты проверок сохраняются в таблице bulletins для аудита; срок хранения согласуется с заказчиком.
Как мы проверяем качество текстов
Набор типовых случаев (разные статусы, флаги качества, серые ячейки, провокационные вопросы в чате) оценивает контакт из администрации или МЧС по трём критериям: понятно, числа верны, нет запретных утверждений. Этот набор запускается автоматически при каждой смене модели или промпта.

Авторизация и безопасность
• Вход по учётной записи для администрации и МЧС, ключи API для исследователей; роль проверяется на каждом эндпоинте на сервере.
• Роль администрации видит только свой район; фильтр по району задаётся на сервере, а не из запроса.
• Токен Earthdata, ключ LLM-провайдера, секреты JWT — только в .env; .env в .gitignore.
• HTTPS, CORS ограничен доменами интерфейсов, лимиты запросов на ключ и на IP.
• Журнал действий специалистов (кто, когда, что) хранится без возможности правки.
• Персональных данных жителей нет; в базе только рабочие аккаунты сотрудников и ключи.
Уведомления
При переходе ячейки на жёлтый или красный уровень сотрудникам с соответствующей ролью отправляется письмо или сообщение в Telegram с ссылкой на карточку ячейки. Точный канал и адресаты определяются с заказчиком; рассылка жителям в MVP не входит.
Развёртывание
Docker Compose: API, конвейер (отдельным контейнером), PostgreSQL с PostGIS, растровое хранилище. Логи и метрики конвейера (успешный цикл, число новых продуктов, возраст последних данных) видны в админ-панели; если данные устарели, ячейки получают серый статус.
9. Фронтенд
Единое веб-приложение с тремя витринами (администрация, МЧС и государство, исследователи); доступные экраны зависят от роли (раздел 2). Команда фронта работает только через API из раздела 8.
Визуальный стиль
Тёмный «геопространственный HUD» по референсу заказчика (вертикальная инфографика): тёмно-синий фон, полупрозрачные панели с неоново-бирюзовой рамкой, радужная раскраска рельефа по высоте, стопка слоёв, список иконок слева, легенда, нижняя полоса шагов.

Правила интерфейса
• Каждый показатель сопровождается датой данных и бейджем источника; устаревшие данные помечаются явно.
• Текст ИИ всегда помечен «сгенерировано ИИ» и не показывается без блока «Чего мы не знаем».
• Во всех местах статусы называются «нужна проверка», а не «опасно»; формулировки согласуются с МЧС.
• Порядок действий не показывается как рекомендация системы: только кнопка «передать специалисту».
• Доступность: контраст текста не ниже 4.5:1, работа с клавиатуры, подписи не меньше 12 px, для дальтоников — иконки и текст статуса.

Люди и решения
• Контактное лицо в администрации и в МЧС (вы подтвердили, что оно есть): нужны два-три часа его времени на этапах 0, 3 и 5.

• Согласование формулировок статусов и текстов бюллетеней с МЧС: что можно писать в публичном уровне, что только в закрытом.

• Языки: подтвердить ru и ky и назначить человека, который проверит кыргызские тексты ИИ.
• Лицензия на открытые выгрузки и API для исследователей (например, CC BY 4.0): выбирает заказчик.
Что мы делаем сами и не просим у вас
Мы сами подбираем источники данных (раздел 4), выбираем размер ячейки по результатам этапа 0, пишем конвейер, аналитику, интерфейсы и тесты, а также открываем файлы NISAR, чтобы проверить пути HDF5 и знак смещения. Эти проверки входят в этап 0 и не требуют от вас никаких действий, кроме учётной записи Earthdata.

Ложные тревоги и пропуски
Доверие к системе падает или, хуже, возникает ложная уверенность
Ретроспективная проверка (этап 3) с честным отчётом; статус всегда «нужна проверка», никогда «безопасно»; журнал решений людей служит обратной связью
ИИ выдумывает числа или причины
Пользователь получает неверное объяснение
ИИ объясняет только пакет фактов; проверка чисел; запрещённые формулировки; шаблонный запасной режим; исходящие тексты утверждаются человеком
Текст прочитан как прогноз или разрешение на действия (эвакуация, «всё в порядке»)
Реальный вред из-за лишней тревоги или лишнего спокойствия
На экране постоянный блок «Чего мы не знаем»; система не даёт рекомендаций по действиям, только передаёт специалисту; формулировки согласованы с МЧС
Формат файлов или доступ к API меняется; в HyP3 продукты удаляются через 14 дней
Конвейер ломается или теряется история
Результаты сохраняются у нас с версией; паспорт продукта; интеграционные тесты на реальных ответах серверов; оповещение при пропуске цикла
Смещение «вдоль луча» путают с реальным движением склона
Неверная интерпретация величины и направления
В пояснении и на паспорте слоя указано, что измеряется смещение в направлении на спутник; крупные выводы проверяет эксперт
Публичные данные раскрывают лишнее о частных участках или вызывают панику
Давление на жителей и власти
Публичный уровень — только агрегаты; ячейки и тексты бюллетеней — только авторизованным ролям
Не хватает времени
В демо нет реальных данных
Порядок этапов таков, что уже после этапа 2 на карте видны реальные статусы; упрощённый набор раздела 11 указан выше
Чего нельзя обещать
Система не прогнозирует оползни, не определяет время события, не заменяет геолога и не может утверждать, что участок безопасен. Она показывает, где данные отличаются от нормы и что участок стоит проверить.

Данные и документация проверены на 14 ноября 2026; перед стартом этапа 0 их нужно проверить заново, потому что продукты NISAR выходят как временные и меняются.
